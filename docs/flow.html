Six pictures of a four-verb protocol

Postern is 2,168 lines of prose and no diagrams. Almost all of its difficulty sits in one place — the state machine deciding whether a run is allowed — and that machine is described across five sub-sections and one eight-row table. This is that machine, drawn.

A · §2, §4, §5 — TopologyTwo surfaces, joined at the runner

Postern looks like one protocol and behaves like two, with opposite security models, meeting in a single process.

Everything a client touches is unauthenticated, loopback-bound, and carries no agent identifier at all — §2.2 makes the port the agent's address, so a runner serves exactly one agent and none of the four verbs needs to name it. Everything the runner touches upstream is the inverse: HTTPS-only, bearer-authenticated, and addressed by a two-segment identifier.

The runner is where those two models are reconciled, and it is also the only party holding state. A client is stateless by construction; a distributor answers each check fresh. The runner is the one that caches an answer, persists it across a restart, and computes the deadlines. Every hard rule in §5 is a rule about what the runner remembers.

B · §2, §3, §4 — LifecycleA run, end to end

Four verbs, but only two of them can ever be refused on entitlement grounds.

The ordering below is not mandated anywhere — a client may call the verbs in any order — but it is the only ordering that lets a client know what it is doing before it does it. status reports the conformance level, so a client learns whether run and stream exist at all; describe reports the input contract, so it learns what to send. Both are required to answer at Level 1 and both are required to answer without an entitlement, which is precisely what lets a client render an agent it cannot yet run.

The entitlement check is invisible from the client's side. It happens runner-side, only when the cached answer has expired, and its failure surfaces to the client as an ordinary error on run or stream.

Conformance is cumulative, and a verb above the level is a permanent 501 — never a degraded answer

The 501 cells matter more than they look. §3 forbids a Level 2 runner from answering stream with a single-shot response, because a client that asked for a stream and silently received one event cannot distinguish “not supported” from “finished instantly”. And the code has to be not_implemented rather than unavailable: a level is a permanent property, so inviting a retry that can never succeed would be a lie about the runner rather than about the request.

A code marked for one side is not merely unusual on the other — it is unconstructible there, so a client receiving one has learned something about the responder rather than about its request. There is deliberately no 401 anywhere in the protocol; §5.5 explains why, and Figure 5 draws it.

C · §5.1, §5.4, §5.7 — The gateEverything §5 says, as one walk

Eight rows of table, five sub-sections and two nested time bounds reduce to a single traversal with three possible endings.

This is the part of Postern an implementer actually has to get right, and it is the part the prose spreads furthest. §5.1 handles the no-distributor case, §5.4 sets the re-check deadline, §5.7.1 adds grace, §5.7.3 handles a runner that has never been told anything, and §5.7.4 handles a 404. The table at the end of §5.7.4 collects the results but not the order in which the questions are asked.

Asked in order, they terminate in exactly three ways — and the specification names the rule underneath them itself.

“Unreachable answers unavailable; refused answers not_entitled.” A runner that cannot find out invites a retry. A runner that has been told no does not pretend the answer might change.

D · §5.3, §5.4 — The windowWhy checked_at is the distributor's clock

One sentence in §5.3 stops two caches from stacking, and it is the sentence most likely to be implemented backwards.

checked_at means the moment the distributor last consulted the authority — not the moment it answered, and emphatically not the moment the runner received the answer. A distributor serving from its own cache reports the age of the underlying read.

The obvious alternative — let the runner stamp its own clock on receipt — validates identically and produces a silently longer window. The distributor's cache age becomes invisible to everyone, the two caches run back to back, and stale_after_seconds describes half of the real worst case while claiming to describe all of it.

E · §5.5, §7 — The blind spotFour questions, one answer

Postern defines no 401 and forbids 403 on a distributor. That is a deliberate loss of information, and it costs its own implementers the most.

A 403 confirms that an agent exists. Over a guessable identifier space that turns the entitlement endpoint into an enumeration oracle for a private catalogue, so §5.5 collapses four distinct situations into one identical response — including, notably, the distributor's own routing bugs. A listing type nobody wrote a case for authenticates normally and then 404s a buyer who owns the thing, byte for byte the way a correct refusal does.

Which is why §5.5 ends with an obligation that has nothing to do with the wire format: a distributor MUST cover each branch of its internal resolution with a test of its own, out of band — one per branch, not one per happy path. No client will ever report this class of bug, because no client can see it.

F · §4.3 — StreamThe event contract

Five event types, two hard rules about ordering, and one invariant that makes progressive rendering trustworthy.

stream takes the same request body as run and returns text/event-stream. Its list of event types is explicitly designed to grow — a client MUST ignore an unrecognised event name rather than aborting, which is how the list extends without a version bump.

G — Reading notesFive things the drawing surfaced

Three are properties worth knowing before implementing. Two were places where two conforming implementations could reasonably differ, and are now settled in the specification.

  1. All of the difficulty lives in one component

    A client holds no protocol state; a distributor answers each check fresh. The runner is the only party that caches an answer, persists it across a restart and evaluates deadlines against it. That means the whole of §5 — every MUST about windows, grace, persistence and re-checking — collapses into a single unit that can be built and tested without any HTTP at all: feed it a clock and a sequence of check outcomes, assert the state and the verdict. Figure 3 is that unit's test matrix.

    §5.4, §5.7.2, §5.7.3

  2. unknown is two states, told apart by an absent field

    “Inside grace, still running, with a deadline” and “never checked, cannot start” are both reported as entitlement.state: "unknown", and the only thing separating them is whether checked_at is present. The specification argues this costs nothing — and in the protocol it doesn't — but it is a real hazard in a typed client, where an Optional timestamp that defaults to now on deserialise silently converts “cannot start” into “running, with a fresh window”. Both shapes validate against status.schema.json. This is the one place I would insist on a test rather than a type.

    §4.4, §5.7.3

  3. A first-ever 404 reports a stale_after_seconds the runner chose

    §5.7.4 sends a 404 straight to revoked — it is an answer, not an outage, so §5.7.3's never-checked path does not catch it. §4.4 then requires both checked_at and stale_after_seconds whenever the state is revoked, and the 404 body carries neither: §5.5 requires it to be constant.

    So the runner supplies both — its own receipt time, and its own re-check cadence, reusing the distributor's last stale_after_seconds where it has one. On a first check it has none, which is what a token revoked before its runner ever ran produces: worth building for rather than treating as exotic. Nothing in the payload marks the number as the runner's own, and under revoked that is the honest answer — there the field says when this runner will ask again, rather than bounding the distributor's revocation risk.

    §4.4, §5.7.4

  4. Idempotency-Key support is declared, and saves less than it looks

    §4.2 says run is not idempotent and that a runner MAY honour an Idempotency-Key. Nothing declared whether a given one does, so a client whose request died in flight could not tell whether retrying was free or whether it was buying the work twice — while §2.3 was already varying that same client's CORS preflight by the answer.

    capabilities.idempotent_retry declares it now, and declaring it forced fixing what honouring means: a repeat key MUST NOT execute the agent again and is answered with the first execution's result. The narrower half is the part worth reading twice. §4.5 aborts an abandoned run and discards its output, so a key cannot rescue the disconnect that section is about; what it saves is the retry whose first attempt finished and whose answer was lost on the way back — which, from the client's side, looks exactly the same.

    §4.1.2, §4.2, §4.5

  5. A delta mismatch is settled in favour of done

    Concatenated delta.text MUST equal done's output.value. That binds the runner, and for a while nothing said what the client on the other end does when it is broken — the one surprise in the protocol with no receive-side rule, where unrecognised error codes, event names, validation members and input types all have one.

    §4.3 now answers it. A client SHOULD prefer done's output.value, because §4.2 makes the run response the result and the deltas were a preview of it; it MUST NOT report the run as failed on that ground, which is §4.1.4's line between a run that succeeded and a client that rendered it wrongly. A SHOULD rather than a MUST because a client writing deltas to standard output has already emitted them and a scrolled terminal cannot be taken back — so one that can replace what it showed does, and one that cannot may say the streamed text was superseded.

    §4.3, §4.1.4

Notes 3, 4 and 5 were reader questions rather than defects — the kind CONTRIBUTING.md calls “the most useful reports we get: ambiguity found by a reader is ambiguity found before it is baked into implementations.” Each has since been answered in the specification, and each note describes the answer rather than the question it started as.
